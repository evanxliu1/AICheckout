# Extension

A Manifest V3 extension (`extension/`, Vite + `@crxjs/vite-plugin`, React 19, `@ai-checkout/ui`). The service worker owns all state in `chrome.storage`; the popup and onboarding pages are thin clients that send typed messages. State is plain local storage by default; a passphrase vault is optional. The popup reads a cart at any web store (Phase 13b) with the generic reader `@ai-checkout/cart-reader`, the only reader since Phase 15.1 retired the three legacy adapters (2026-10-20, [retired adapters](#retired-adapters-phase-151)). Since Phase 14.2 (2026-10-11) the tab's store is matched on the device against the bundled merchant release `MERCHANTS_V1` ([store matching](#store-matching-phase-142)). The automatic cart badge has its own page: [Cart badge](cart-badge.md).

**Phase 15.1 (2026-10-20, branch `phase15-1-retire-adapters`, agent-verified by the implementer's gates and the independent Opus review):** `extension/src/checkout/adapters/`, `page-reader.ts`, `state/savings.ts`, `components/SavingsHistory.tsx`, `scripts/observe-amazon-cart.mjs` and the adapter tests and fixtures are gone; `merchants.ts` keeps `GENERIC_READER_VERSION` and `isWebUrl` only; `probeSchema` accepts `generic-us-online` with `generic-reader-v1` only and `cartSnapshotSchema` any store id with that version; the popup's default store is the generic one and its select offers the tab's store and "Another U.S. online store"; the stored `disabledMerchants` setting maps to hosts once on read; order detection and the savings history are removed (`savings` stays in schema 3 as a tolerated, never-written field). Both content scripts shrank: the manual reader from 45,740 to 36,850 bytes, the badge from 49,946 to 40,412 bytes.

Verified 2026-10-03 on branch `s2-m7-extension-ui` (Stage 2 M7, merged with `main` after M5 and again after M10 part 1 and Tailwind 4) by running `npm test --workspace=ai-checkout-extension` (28 vitest files, 688 tests, plus 6 `node --test` package tests) and the Playwright specs (`npm run test:browser`: 14 passed, 3 skipped by design; `npm run test:catalog:browser` and `test:package:browser` passed). Earlier: verified 2026-10-02 on branch `s2-m6-extension-state` (Stage 2 M6, merged with PR #26; M5 merged with PR #27 made `CATALOG_V3` the bundled catalog) by reading the code and running `npm test --workspace=ai-checkout-extension` (23 vitest files, 608 tests including the rewards engine suites, plus 6 `node --test` package tests) and the Playwright specs (`npm run test:browser`: 10 passed, 3 skipped by design; `npm run test:catalog:browser` and `test:package:browser` passed).

## How it works

### Worker and messages

[`src/background/index.ts`](../../extension/src/background/index.ts) restricts both storage areas to `TRUSTED_CONTEXTS` (on worker start, `onInstalled` and `onStartup`), builds the vault service and the badge service, and routes every `chrome.runtime` message through [`routing.ts:routeMessage`](../../extension/src/background/routing.ts) (sender-based; details on [Cart badge](cart-badge.md#message-routing)). `checkout:*` and `settings:*` are accepted only from the popup and onboarding page URLs. After any page request the worker broadcasts `badge:changed` so open badges re-read their view. Tab updates and removals invalidate saved carts. `onInstalled` with reason `install` opens onboarding.

Requests (`requestSchema` in [`state/contracts.ts`](../../extension/src/state/contracts.ts)): `checkout:get-state`, read-only `catalog-cards` (up to 20 card IDs whose terms the wallet editor needs), `refresh-catalog`, `save-wallet`, `read-cart`, `rates`, `compare`, `clear` (`delete-savings` and the internal `record-savings` went with the savings history in Phase 15.1); vault: `checkout:vault-status|create|unlock|lock|delete|remove`. Mutating requests other than `clear` carry `expectedRevision` and fail if the state moved (another window). Every successful response carries `state`, the comparison, a notice, `catalog` and `cardIndex` ([`service.ts:pageResponse`](../../extension/src/state/service.ts)): `catalog` is the catalog in effect cut by [`catalog-slice.ts:catalogSlice`](../../extension/src/state/catalog-slice.ts) to the owned cards (plus the cards a `catalog-cards` request names), every merchant and what those cards refer to (programs, brands, gates, sources), and `cardIndex` lists every card's id, name, short name and issuer for search; with two owned cards a response is under 80 KB against about 800 KB for the whole bundled catalog ([decision](../decisions/2026-10-03-extension-ui-v3.md)). `responseSchema` checks the slice only for shape, since it may hold no cards. Pages use it and never load the bundled catalog (they import keys and limits from [`state/keys.ts`](../../extension/src/state/keys.ts), not the worker's `service.ts`). `responseSchema` accepts the v3 rule statuses, uncertainty codes, `no-accepted-card`, `notAccepted` and the estimate fields `programId`, `minRewardUnits`, `maxRewardUnits`, `unitValue`.

### State and migration

`appStateSchema` (schema 3): `revision`, `wallet`, `purchase`, manual `cart` snapshot, `savings[]` (tolerated, never written since Phase 15.1), `pendingNotice`, `comparison` metadata and `walletCatalogVersion` (the catalog the wallet was last checked against). The catalog cache is not in the state; it lives under `CATALOG_KEY` and is written in the same `storage.set` as the state it belongs with. [`state/service.ts:createStateService`](../../extension/src/state/service.ts) serialises operations in one promise queue and treats storage as authoritative so popup closure or worker shutdown loses nothing.

Migration, once on load ([`migrate.ts:migrateState`](../../extension/src/state/migrate.ts)), in one write of both keys: schema 1 (pilot) drops usage rows for rule IDs its catalog lacks; schema 2 moves its embedded cache to `CATALOG_KEY` (a cache already under that key wins unless its release has a lower sequence), stamps `walletCatalogVersion`, bumps the revision and clears the saved comparison. A one-time notice is kept in `pendingNotice` until shown. With the vault on, migration happens on the first unlocked read and re-encrypts the smaller schema 3 state. An unreadable catalog cache is ignored (bundled terms).

Reconciliation ([`migrate.ts:reconcileState`](../../extension/src/state/migrate.ts), [`wallet.ts:reconcileWallet`](../../extension/src/state/wallet.ts)): when `walletCatalogVersion` differs from the catalog in effect (an extension update changed the bundled catalog, the catalog in effect switched between cached and bundled as one expired or the other is newer, or the cache was dropped), load drops usage rows, choices, gate answers and point values whose IDs the catalog lacks (the engine throws on them), and usage rows whose rule changed when the old catalog is still at hand (`catalogByVersion`: the cached release or the bundled catalog; rules are compared in v3 form, `ruleTerms`, so a v2 rule carried unchanged into v3 keeps its rows: [decision](../decisions/2026-10-03-bundled-catalog-v3.md)), with the migration notice and a revision bump; if nothing is dropped only the stamp changes. Owned cards the catalog lacks stay and block comparisons (`unknown-owned-card`). `save-wallet` refuses a wallet with anything the catalog in effect lacks (`validateWallet`).

### Optional vault

[`state/vault-service.ts:createVaultService`](../../extension/src/state/vault-service.ts) wraps the state service with a storage adapter. Statuses: `unprotected` (plain record or nothing yet; the default), `locked`, `unlocked`, `damaged`. `vault-create` encrypts the existing plain state; `vault-remove` (needs the passphrase) decrypts back to plain storage and drops the session key; `vault-delete` clears everything. The derived key lives only in `chrome.storage.session`. Legacy MVP keys (`openaiKey`, `cachedCards`, …) are removed on status checks.

### Catalog refresh

The catalog in effect ([`state/catalog.ts:currentCatalog(cache, now)`](../../extension/src/state/catalog.ts)) is, of the cached release's catalog (v1, v2 or v3) and the bundled `BUNDLED_CATALOG` (`CATALOG_V3`, since Stage 2 M5 `2026-10-02.expansion.1` and since the Phase 9 renewal, PR #50, `2026-10-05.renewal.1`; `CATALOG_V2` before), the one valid now; when both are valid, the one with the later `verifiedAt` (the cached release on a tie); when both have expired, again the one verified later; when neither is valid otherwise (one not yet valid), the cached release, so comparisons report its state ([decision](../decisions/2026-10-03-newest-valid-catalog-wins.md), [both expired](../decisions/2026-10-03-expired-catalogs-keep-answers.md)). An expired catalog in effect never prunes choices, gate answers or point values (`reconcileWallet(…, { keepOptions })`, also in `validateWallet`); comparisons get an in-memory copy without unknown IDs (`wallet.ts:engineWallet`). Only the worker imports this module. `checkout:refresh-catalog` is user-triggered from the popup and exists only in builds with `VITE_CATALOG_API_URL` ([`catalog-config.ts`](../../extension/src/catalog-config.ts)); the URL must be a fixed HTTPS `/v1/catalog` endpoint or the build fails. [`prepareCatalogUpdate`](../../extension/src/state/catalog.ts) accepts every catalog schema and rejects: invalid schema, a null release after one was cached, expired or future releases, a lower sequence, same sequence with different content, a reused version. On acceptance it drops usage rows whose rule changed or disappeared, and choices, gate answers and point values whose IDs the new catalog lacks, stamps `walletCatalogVersion`, clears the saved comparison and writes cache and state together; a check that finds nothing new writes only `lastCheckedAt` to the cache. A release older than the bundled catalog in effect is cached (the reference for the next sequence check) without touching the state ([decision](../decisions/2026-10-02-extension-state-v3.md)).

### Retired adapters (Phase 15.1)

From Phase 3 to Phase 14 three JSON site adapters (`best-buy-us` `bestbuy-summary-v1` on `bestbuy.com`/`www.bestbuy.com` `^/cart/?$` and `^/checkout(?:/.*)?$`; `newegg-us` `newegg-summary-v1` on `secure.newegg.com` `^/shop/cart/?$`; `amazon-us` `amazon-summary-v1` on `www.amazon.com` `^/gp/cart/view\.html$` and `^/cart/?$`) read those stores' cart pages through one interpreter (`page-reader.ts:readCheckoutPage`, selectors per adapter, validated at build time), carried the stores' names ("Amazon US") and unverified `orderConfirmation` URL patterns for the order question. **Legacy since 2026-10-06** ([decision](../decisions/2026-10-06-reader-shows-only-certain-amounts.md)), **retired 2026-10-20** by Evan's directive of 2026-10-19 ([decision](../decisions/2026-10-19-retire-legacy-adapters.md)): the generic detector and reader read every page, the merchant release names the three stores (`Amazon`, `Best Buy`, `Newegg`; the three release records and the catalog's merchant profiles are unchanged), and the before-and-after readings are recorded in [`docs/evals/legacy-adapter-retirement.md`](../../docs/evals/legacy-adapter-retirement.md) (part 1, the committed observed fixtures: the same amounts at Best Buy and Newegg, nothing shown on the reduced Amazon fixtures where the adapter read the subtotal; part 2, fresh captures, is milestone 15.1m). The reader harness's legacy mode (`evals/reader/legacy-entry.ts`) went with them; `runs.json` rows from before keep their `legacyBundleSha256`.

### Store matching (Phase 14.2)

Since 2026-10-11 ([plan](../product/phase-14-merchant-database.md#4-how-it-works-at-checkout), [decision](../decisions/2026-10-11-extension-on-the-merchant-release.md)) [`store-match.ts:storeForTab(url)`](../../extension/src/checkout/store-match.ts) (imported by the worker and the extension pages only, never by a content script) resolves a tab URL against the bundled merchant release `MERCHANTS_V1` ([Merchants](../domain/merchants.md#merchant-release-records-phase-141)) with the Zod-free matcher `matchMerchant` ([Rewards engine](rewards-engine.md#store-matcher-phase-141)): the record whose host is the longest label-boundary suffix of the hostname. It returns `{kind, id, host, name}`: `store` for a matched `merchant` or `marketplace` record (its id and name; until Phase 15.1 the three legacy ids kept their adapters' names, `Amazon US`, now the release's `Amazon`), `generic` (`generic-us-online`, "Another U.S. online store") for an unmatched site, an IP address or a `disabled` record, `processor` for a payment page (PayPal, Shop Pay, Amazon Pay's hosts before `amazon.com`), and null for a non-web page. `host` is the tab's lower-cased hostname (never the path), the key of the per-site switch. `merchantForTab(url)` is that store's id (null for processors and non-web pages). **Matching runs in the worker** (review fix, same day): the content scripts carry no release; a reading names `generic-us-online` on every http(s) page (`manual-reader.ts`; until Phase 15.1 the legacy store on an adapter's URL), and the worker (`badge-service.ts:content`, `browser.ts:readActiveCheckout`) resolves the sender or tab URL with `storeForTab` and writes the matched id to the tab entry or the cart snapshot. A reading that names any other store is refused, so a content script can never name a store, and a release refreshed in the worker (14.6) applies to every page without a new content script. `storeProfile(catalog, id)` is the engine profile for a store under a catalog v3: a release record through `releaseProfileFor` (a `default` record defers to a profile the catalog authors, so Best Buy and Newegg keep `electronics` until 14.4), else the catalog's own profile, else the generic profile; undefined for processors, disabled records, unknown ids and v1/v2 catalogs. `merchantOption(catalog, id)` wraps it as the `{ merchant }` option, which every comparison passes: the badge view ([Cart badge](cart-badge.md#worker-side)), `checkout:compare`, the saved comparison's recompute and `checkout:rates` ([`state/service.ts`](../../extension/src/state/service.ts)). `storeEvidence(id)` is the line shown where a bonus category applies ("Codes as a supermarket (its own store pages and a public merchant-code lookup agree).", "(named in card terms).", or since 2026-10-11 for a `definition` record "(its own pages; fits American Express's supermarket definition)." with the issuer taken from the catalog card that cites the release's issuer source, "an issuer's" when none does, or for an `mcc` record "Codes as a supermarket in public purchase-card data (mostly in-store)." ([mcc basis](../decisions/2026-10-11-mcc-evidence-basis.md)); no partnership is implied), null for a `default` record, the generic store and ids without a record. `merchantName(id)` names the generic store or a release record (since Phase 15.1 the three former adapter stores too: `Amazon`, `Best Buy`, `Newegg`); anything else is "Unsupported merchant". The worker and the pages import the release and the matcher through the `@ai-checkout/rewards-core/merchants-v1` and `/merchant-match` subpath exports (no Zod); [`merchants.ts`](../../extension/src/checkout/merchants.ts) keeps only `isWebUrl` and `GENERIC_READER_VERSION` for the content scripts. A processor page is read by the content script like any hinted page but the worker answers `{show: false}` and stores nothing, so no badge appears and nothing leaves the device beyond that reading; the popup refuses it before injecting the reader. The bundled seed `2026-10-10.seed.1` has only the three legacy stores and 15 processors, so no store is newly named until 14.4; the fixture release in `test-cases.ts` covers named, evidenced, disabled and processor records in the unit tests.

### Merchant release refresh (Phase 14.6)

Since 2026-10-11 ([plan §4 "Freshness"](../product/phase-14-merchant-database.md#4-how-it-works-at-checkout), [decision](../decisions/2026-10-11-hosted-merchant-release-details.md)) hosted builds (`VITE_CATALOG_API_URL` set) also fetch the published merchant release from `GET /v1/merchants` on the same origin ([`catalog-config.ts:fetchPublishedMerchants`](../../extension/src/catalog-config.ts)). [`state/merchants.ts`](../../extension/src/state/merchants.ts): `prepareMerchantUpdate` validates the body with `merchantsResponseSchema` (the Zod `merchantReleaseSchema` inside) and rejects an invalid body, a null release after one was cached, a release verified or published in the future, a lower sequence (rollback), the same sequence with different content and a reused version; a check that finds nothing new writes only `lastCheckedAt`. `currentMerchants(cache)` is the release in effect: of the cached and the bundled `MERCHANTS_V1` the one with the later `verifiedAt` (the cached on a tie); without a cache, or with an unreadable one, the bundled release; a site neither knows is the matcher's generic store, so a comparison is never blocked. **Worker:** `createStateService`'s `load` and the badge service's `content` and `view` read the cache on every request (`readMerchantCache`) and pass the release to `storeForTab`, `storeProfile` and `merchantOption`; `createStateService`/`createVaultService` take `fetchMerchants` as their sixth argument. **Pages:** popup, onboarding and badge read the cache once before the first render ([`state/merchants-page.ts:loadMerchantsInEffect`](../../extension/src/state/merchants-page.ts) → `store-match.ts:setMerchantsInEffect`), so the tab's store, names and evidence lines agree with the worker. **When:** `checkout:refresh-catalog` ("Check for updated terms") refreshes the catalog and then the merchants whatever the catalog check's outcome, best effort (the notice or error stays about card terms); the worker creates one `chrome.alarms` alarm `refresh-releases` (`delayInMinutes` 2, `periodInMinutes` 10,080) on install or browser startup **only when `chrome.alarms.get` finds none** (re-creating it would restart the week; review fix 2026-10-11) and, when it fires, runs `handle.refreshReleases(90_000)`: the catalog (`skipped` while the vault is locked or damaged, since the wallet cannot be reconciled) then the merchants, each `skipped`, `ok` or `failed`; when either failed (the API asleep, offline) one retry alarm `refresh-releases-retry` follows 5 minutes later, never a second; open badges are told `badge:changed`. `readMerchantCache` memoizes the parsed cache by the row's `release_hash` and `lastCheckedAt`, so a request re-validates the release only after a write, and `store-match.ts` indexes each release object once. Content scripts never see the release.

### Manual cart read (popup)

[`checkout/browser.ts:readActiveCheckout`](../../extension/src/checkout/browser.ts) injects `src/checkout/content.js` into the active tab's top frame (isolated world) via `activeTab` + `scripting`, calls `window.__AI_CHECKOUT_readSummary`, and stores a snapshot bound to tab ID, document ID and a SHA-256 of the URL. `validateActiveCheckout` re-reads the same document before a cart-based comparison is shown again. Any http(s) tab can be read (`merchantForTab` non-null); a non-web page (`chrome://`, the extension's own pages) gets the `unsupported-page` message, and a payment processor's page (Phase 14.2) the `payment-page` message without injecting anything.

**Since Phase 13b (2026-10-09, [plan](../product/phase-13-reader.md#phase-13b-the-reader-in-the-extension-planned-2026-10-09))** the content script runs [`manual-reader.ts:readManualCart`](../../extension/src/checkout/manual-reader.ts) (since 13c the reading of `readAnyCart`, which the badge shares): on every http(s) page `readCartPage(document, { url })` from [`@ai-checkout/cart-reader`](../../packages/cart-reader/README.md) (until Phase 15.1 a URL a legacy adapter matched got the adapter's `readCheckoutPage` instead) (Phase 13c: the detector in front of the reader; a page it does not recognise as a cart or checkout, a `no-hint` product page included, is `not-a-cart` since the 13c review fixes, `520a75c`; `withheld` before), returning only the reading. A shown USD amount becomes a reading naming `generic-us-online` (the worker resolves the tab's store, Phase 14.2), kinds `afterCredit` → `total`, `estimatedTotal` → `estimated-total`, `subtotal` → `subtotal`, `extractorVersion` `generic-reader-v1` (`GENERIC_READER_VERSION` in `merchants.ts`); a zero total is `empty-cart`. Shown in another currency → `unsupported-currency` (the existing "USD only" message); withheld for any reason → `withheld` ("The cart total could not be read with certainty on this page. Your cards are compared by rate.", [`read-copy.ts`](../../extension/src/checkout/read-copy.ts)); not a cart page → `not-a-cart` (the popup's read on open says nothing; "Read cart amount" shows "This page doesn't look like a cart or checkout page…"). An empty cart is checked before `not-a-cart`, a non-USD cart after it. `browser.ts` requires the reading to name `generic-us-online` with `generic-reader-v1` on read (the probe contract enforces the same), writes the tab's resolved store into the snapshot, and compares the reading against the snapshot on validation. Privacy: the generic reader reads the page's visible summary text and, for currency only, structured data (JSON-LD `priceCurrency`), currency meta tags, attributes containing "currenc" and the URL's TLD; nothing but the reading (kind, amount, currency, or a reason code) leaves the page. Re-validation is layout-dependent: a cart drawer closed between Read and Compare makes the re-read differ and gives "cart or page changed", failing safe.

Contracts ([`contracts.ts`](../../extension/src/checkout/contracts.ts)): since Phase 15.1 `probeSchema` (a content script's reading) accepts `merchantId` `generic-us-online` only, and `cartSnapshotSchema` (written by the worker) any id of 1–100 characters (since 14.2: the snapshot carries the store the worker resolved for the tab, a release record's id included); both accept `extractorVersion` `generic-reader-v1` only, so the retired adapters' `*-summary-v1` readings and any other version string are refused. A stored state's saved `cart` goes through `storedCartSnapshotSchema`: a snapshot an adapter wrote before 15.1 reads as no saved cart (a comparison tied to it asks for a new read), so an upgraded install's state never reads as damaged (Opus review fix, 2026-10-20). The unavailable reasons are `unsupported-page`, `empty-cart`, `unsupported-currency`, `withheld` and (13c) `not-a-cart`; the adapters' `summary-missing`, `ambiguous-amount` and `page-loading` codes and their copy were removed in the 15.1 review (nothing produced them), and a reply the contract refuses reads as `withheld` (the rates view), as `ambiguous-amount` did. The automatic badge ([Cart badge](cart-badge.md)) runs the same split on every https page since 13c.

### Usage reporting (Phase 15.3)

Since 2026-10-20 (branch `phase15-3-telemetry-client`; [plan](../product/phase-15-release-a.md#4-milestones) row 15.3, [design decision](../decisions/2026-10-19-release-a-telemetry-design.md), [implementer decision](../decisions/2026-10-20-telemetry-client-details.md); the event set is the public dictionary [`docs/telemetry/events.md`](../../docs/telemetry/events.md), generated from the API's contract `packages/catalog-review/src/telemetry.ts` by `npm run telemetry`, checked by `telemetry:check` in CI). **Worker only:** [`state/telemetry.ts:createTelemetry`](../../extension/src/state/telemetry.ts) builds every event from what the worker holds, adds the envelope (`event_id`, `client_at`, `install_id`, `install_month` and the `days_since_install` bucket from `installedAt`, the consent and schema versions, the extension version from the manifest, the catalog and merchant release versions in effect read from the public caches, `reader_version` `generic-reader-v1`), parses it with `telemetryEventSchema` and drops anything the contract would refuse (a fixture catalog version in a test build, an IP address on a tap), queues it in `checkoutTelemetryV1` (≤ 200, oldest dropped) and flushes through `telemetryClient`: started at once at consent, on each tap and at 50 queued events, otherwise by the `telemetry-flush` alarm (15 minutes, created when the queue fills, cleared when it empties). The queue is read and settled under the module's lock but the request runs outside it, one at a time, and no caller awaits it (since the 15.3 review): a cold or asleep Render instance (up to the 20 s timeout) never delays a badge view, a popup request or the Settings panel; the emit points start their `record` calls without awaiting them. Replies: 2xx removes the batch; 410 (the API's kill switch) clears the queue and pauses sending 7 days; 429, 503 and other 5xx keep the batch and wait `Retry-After` (seconds, capped at a day) or 15 minutes; a network failure waits for the next alarm; any other 4xx drops the batch. **Nothing is queued before Share** except the two taps. **Consent:** `telemetry:consent {granted, source}` from the onboarding screen ([`Consent.tsx`](../../extension/src/components/Consent.tsx), shown after the cards are saved only when `TELEMETRY_ENABLED`; Share and Not now are the same button component and colour; the copy is `CONSENT_COPY`, "a random identifier, so repeated reports can be told apart: no name, email or browsing history", a privacy-policy link to `/privacy/` on the catalog origin) or from Settings ([`TelemetrySettings.tsx`](../../extension/src/components/TelemetrySettings.tsx), the "Sharing usage data" toggle). Share mints a random id (`crypto.randomUUID`), stamps `installedAt`, queues `consent_granted`, then `onboarding_completed` (onboarding only) and `wallet_changed` with the owned card ids, and flushes. Not now or the toggle off (Stop sharing) sets `consent: declined`, clears the id and the queue and sends nothing. **Delete my data** first lets a batch in flight land and blocks new ones, then posts the current id to `/v1/events/delete` and, only on a 2xx, resets to the Stop sharing state; any other answer (429, 5xx, but also 400 or 403) or a network failure keeps the id and tells the shopper nothing was deleted yet. Settings says that turning sharing off makes earlier reports undeletable from the device (the id is gone; they expire at 90 days). **Emit points:** the badge service reports `recommendation_shown` once per distinct recommendation in a tab (`reportedKey` on the tab entry: view, store, reading, payment path, top card; `surface: badge`, `view` amount or rates, `withheld_reason` `withheld` on the rates view, `page` cart or checkout from a word in the sender URL, `store_kind` and `evidence_basis` from the release record, the category from the store profile, the reading's amount and kind, never a typed amount), `badge_expanded` (`badge:expanded`), `badge_dismissed`, `site_disabled`, `amount_typed` (the typed amount against the reading, bucketed); [`background/index.ts:handlePage`](../../extension/src/background/index.ts) reports `recommendation_shown` for a popup comparison backed by a read cart (`surface: popup`, `page: popup-read`) and for `checkout:rates`, `wallet_changed` on `checkout:save-wallet`, `release_refresh` (`manual`, catalog) around `checkout:refresh-catalog`; the alarm handler reports `release_refresh` (`weekly`) for both releases with the versions before and after; the popup sends `telemetry:popup-opened` with what its read on open found (`popup_opened`; not when it opens with no cards or keeps a cart already read or compared in that tab); a failed request is an `error` (`request-failed`, the route kind; ≤ 20 a day). A comparison of a typed amount is not reported: the contract's `amount_kind` names what was read ([decision](../decisions/2026-10-20-telemetry-client-details.md)). **Taps:** "Suggest this store" ([`SuggestStore.tsx`](../../extension/src/components/SuggestStore.tsx), under the popup's Merchant select at a generic store), "Store not recognised? Suggest it" (the badge panel at a generic store, `badge:suggest-store`) and "Report a problem" ([`ReportProblem.tsx`](../../extension/src/components/ReportProblem.tsx), the popup footer: five fixed reasons, no text field) send `store_suggested` and `problem_reported` whether sharing is on or not, with `install_id` null when it is off; the worker resolves the tab's URL itself (`chrome.tabs.get` for the popup's tab id, the tab entry's host for the badge), refuses processors and named stores for a suggestion, and sends only `registrableDomain(host)` (two labels, three under `co.uk`-style suffixes and under `myshopify.com`, whose shops are subdomains; null for an IP). The pages never build an event; `routing.ts` accepts `telemetry:*` from the popup and onboarding page only; content scripts import none of this and their bundles do not contain `/v1/events`.

## Gotchas

- Inspect `dist/manifest.json`; the source manifest omits host permissions, content scripts and badge resources (see [Architecture](architecture.md#gotchas)).
- `e2e/telemetry.spec.ts` needs a build with `VITE_TELEMETRY=1`: it runs in `npm run test:catalog:browser` (dist-catalog-test) and is skipped by `test:browser`, whose dist-e2e has no telemetry, so the other specs' permission set and onboarding flow are unchanged. Its stub API is a local HTTPS server (the worker's fetches do not pass through `context.route`).
- `src/checkout/content.js` (the manual reader) has no web-accessible entry since `1fd1e31`; `executeScript` injects it without one. It bundles `@ai-checkout/cart-reader` (an extension `package.json` dependency resolved through the workspace link, like the other packages); keep Zod out of it (`GENERIC_READER_VERSION` lives in `merchants.ts`, not `contracts.ts`, for that reason).
- Both content scripts are built by a custom esbuild IIFE plugin so the packaged hash does not depend on the checkout path.
- Since the 14.4 seed the worker and extension pages share the `estimates-*.js` chunk that carries the bundled catalog and the merchant release `2026-10-11.seed.17` (641 records): 854,200 bytes (107902 gzip) on 2026-10-11; the content scripts carry neither.
- Only the worker chunk carries the bundled catalog: with `CATALOG_V3` `2026-10-02.expansion.1` it was 587,077 bytes (52,727 gzip; 42,737 with `CATALOG_V2`), the upload ZIP 208,313 bytes (166,831); not re-measured for `2026-10-05.renewal.1` (about 500 bytes more JSON). Popup, onboarding and content-script chunks import no catalog; check with `grep -l 2026-10-05.renewal.1 -r extension/dist` after a build.
- The wallet editor lists all 178 bundled cards by issuer and refuses to save more than `MAX_WALLET_CARDS` (20, `state/keys.ts`, also the schema limit); native-popup browser specs pick cards by name (`checkCards`, `REAL_CARD_NAMES` in `e2e/native-popup.ts`), never by position. Unit tests that fix the clock against the bundled catalog date it from `CATALOG_V3.verifiedAt` (`popup`, `state-service`, `cart-state`, `state-migration`; since the renewal), fixture-based tests use literal dates; `popup.test.tsx` mocks only `Date.now`, so its date must not be later than the real date.
- Styling is Tailwind 4 through `@tailwindcss/postcss` ([`postcss.config.js`](../../extension/postcss.config.js), with autoprefixer); the theme is CSS-first in [`src/styles/globals.css`](../../extension/src/styles/globals.css) (`@theme inline` on `--token-*` and the Ocean `--ac-*` brand values from `packages/ui/src/theme.css` ([UI library](ui-library.md)), no preflight, unlayered utilities, sources limited to `src/`). `space-y-*` keeps Tailwind 3's selector (top margin on each shown child after the first, at class specificity) and a small PostCSS step drops Tailwind 4's own `space-y` rules. Other utilities added later follow Tailwind 4 semantics (`border` sets a solid style, `ring` is 1 px, `hover:` only on hover-capable devices, `space-x`/`divide-*` use the zero-specificity form). The root `package.json` pins `lightningcss` only so npm 11 keeps its platform binaries in the lockfile ([decision](../decisions/2026-10-03-tailwind-4.md)).
- `VITE_E2E_CATALOG_DATE` re-dates the bundled catalog for browser tests; the build refuses it unless the output dir is not `dist` (it uses `dist-e2e`).
- Settings stored before Phase 15.1 may carry `disabledMerchants`; `settingsSchema` accepts and maps it (never writes it), and the badge service rewrites the mapped value once. Other stored shapes are strict.
