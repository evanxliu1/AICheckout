# Card pipeline CLI commands

The commands of [`tools/catalog-pipeline`](../../tools/catalog-pipeline/README.md) (`@ai-checkout/catalog-pipeline`, `npm run pipeline -- <command>`; `--help` prints the usage). The workspace runs on Node 24 type stripping, uses Zod for every file it reads or writes and is tested with synthetic fixtures only. The concept, stages, agents and boundary are on the [card-expansion pipeline](card-expansion-pipeline.md) page; the state record, hashing, packets, gates, queue and builder rules on [card pipeline internals](card-pipeline-internals.md). The merchant pipeline's `pipeline merchants` commands are on [merchant pipeline](merchant-pipeline.md).

## Batch commands

| Command | Behaviour |
| --- | --- |
| `init <batch> --issuer "<Name>" --cards "<a, b>" [--domains a.com,b.com] [--refresh] [--summary "<text>"]` | Writes `pipeline/batch.json` (batch id, issuer name, slug and domain allow-list, requested cards, refresh flag, summary, `createdAt`) and an initial `pipeline/state.json` (research `pending` for the issuer, build and eval `pending`). Batch ids match `^[a-z0-9-]+-\d{4}-\d{2}$`; refuses an existing batch |
| `init <batch> --issuer "<Name>" --refresh-from-freshness <date> [--cards ids] [--summary]` | A refresh batch of the issuer's catalog cards with a `changed` source in that freshness record (or exactly `--cards`, unchanged cards included; a card of another issuer, no record, or no changed card without `--cards` is refused). Seeds from each card's current layer (the newest whose corpus has it): its `cards.json` entry (a real card's from its Phase 7 research entry in `docs/research/cards-2026`, as `build-expansion-cards.mjs` builds one), every one of its `sources.json` entries (`cardIds` narrowed to the batch), the layer's capture hints and an empty `exclusions.json`; `batch.json` gets `refresh: true`, the source hosts as domains and `seed: { freshness, layers }`. Research is recorded `done` with `provenance: "seeded"`; its input hash covers the request, the four seed files and the freshness record, so editing one makes it stale and `next` hands it to the session (`gate-failed`, re-seed) instead of a researcher. Then capture re-captures every source of the batch's cards as new dated captures |
| `status [--batch B] [--json]` | Counts per stage and status per batch, the files in `pipeline/packets/` with their output `absent`, `present` or `present-not-accepted` (an accept failed), cards needing an anchor rebase, and the derived queue (`capture-flagged`, `gate-failed`, `needs-reverify`, `convention-needed`, `scope-question`, `publish`). A seeded batch shows "research seeded from freshness <date>"; without `--batch` it also prints the newest freshness record's counts (`--json`: `freshness`). Writes nothing |
| `next [--batch B] --json` | The single next step `{ kind, batch, stage, issuer?, cardIds?, command?, agent?, code?, until?, reason }`: blocking queue items first, then an anchor rebase, research, the card stages in order, a `wait` for paused cards, build, eval, then `handoff`. Agent steps name the subagent and the `pipeline claim …` command. Every card of a stage that shares a queue code comes in one step (capture-flagged; needs-reverify per issuer; every failed-gate card once one is stuck). While the build config's version is published, it prints the build as `--proposed --version <today>.<batch name>.1` |

## Status derivation

No `running` status, no locks; the queue is never written.

- **Recorded vs derived.** `state.json` records `done`, `failed-gate`, `paused` (with `pausedUntil` and reason `usage-limit`) and `dropped`; `status` and `next` recompute every stage's input hash from the batch files and derive `stale`, `inputs-missing` and `pending`. Cards enter the derivation from `cards.json` (written by research) and get a state entry when a stage first records them.
- **Per-card records for agent stages.** Verify, adjudicate and overlay keep their input hash per card (verify also the draft anchors hash it saw); research is per issuer. Accepted records carry `packetId`, `agentRun`, `model` and `acceptedAt`.
- **Stage inputs.** research: the issuer's request and the researcher agent file; capture: each source's id, URL and kind plus its capture hint; extract: the manifest SHA-256 of each source and the default extraction configuration with limits; draft: the trace, the manifest hashes, the research file and the draft script; verify: the draft case's labels hash, the product-note labels and the verifier brief; adjudicate: the verifier's findings for the card and the batch's `general.md` and issuer conventions; apply: the full draft case and adjudicated findings; overlay: the corpus case's labels hash, the conventions and `reward-programs.json`; build and eval: every active card's corpus case and overlay entry, `merchants.json` and `reward-programs.json`.
- **Propagation.** `stale` propagates downstream, except that an apply stale only through its own inputs (the draft anchors moved) leaves the overlay done. A stage with a missing hashed gitignored input (draft without its trace) or missing inputs it must run with (captures, for extract and draft) is `inputs-missing`; a stage done with a matching hash stays done; a computable hash that differs is `stale` even without the captures (and its downstream with it), and `run` skips the card there. The labels hash leaves out `anchors`, `anchor`, `anchorMethod`, `quote(s)`, `evidence` and `draftNotes`; `issuerWording` is a label.
- **Retries.** After two failed attempts a CLI stage is no longer proposed as `run`: `next` returns a `queue` step `gate-failed` owned by the session.

## CLI stages

`run capture|extract|draft|apply|build|eval [--batch B] [--only ids] [--concurrency N] [--wait-minutes N]` runs the cards whose stage is `pending`, `stale` or `failed-gate` with upstream done, through the wrapped script, then records each card. `extract` refuses when `CI` or `RENDER` is set.

## Agent stages

| Command | Behaviour |
| --- | --- |
| `claim <research\|verify\|adjudicate\|overlay> --issuer <slug> [--batch B] [--release]` | Writes `pipeline/packets/<stage>.<issuer>.<n>.json` (gitignored: absolute paths): random `packetId`, batch, issuer and issuer name, card IDs (verify, adjudicate, overlay: the issuer's cards pending, stale or failed there; verify also a rejected drop-card), `undraftedCardIds` for verify and adjudicate, absolute input paths with their SHA-256, one absolute output path, `claimedAt`; overlay packets list the `corpusCaseSha256` each entry must carry. The findings file is hashed as `verificationFileSchema` parses it (defaults such as `reason: null` or `addedIssues: []` filled in), as the gates hash it, so an omitted optional field does not break accept. Refuses a second open claim on the stage and issuer; `--release` marks the open packet `released` (kept). Prints the packet path and the agent to start |
| `accept <stage> --issuer <slug> --agent-run <id> [--model <id>] [--duration-ms N] [--tokens N] [--dry-run]` | Reads the output (research `research/<issuer>.json`; verify and adjudicate `verification/<issuer>.json`; overlay the fragment `overlay/<issuer>.json`), which must carry the packet's `packetId`, `batch` and issuer name; refuses changed input files and cards outside the packet; runs the stage gates below. Success: issuer record and each packet card's record get `packetId`, `agentRun`, `model`, `acceptedAt` and the input hash (verify also the draft `labelsHash`/`anchorsHash`); the issuer record gets `durationMs` and `tokens` (from the subagent's completion notice; tokens per card = tokens / packet cards); the packet becomes `accepted`. Failure: `failed-gate` (not with `--dry-run`), the packet stays open, errors name paths and fields only (quoted values redacted). `--agent-run` is required even in a dry run |
| `resolve capture-flagged --source <id> --reason <code>` | Records an accepted capture flag (`expected-short-page`, `false-positive-flag`, `keep-existing-capture`) with the capture hash in `state.json` `resolvedFlags`, and re-evaluates the cards of that source |
| `lint-labels [--batch B \| --dir D] [--json]` | The label-evidence lint as a report: findings raised, acknowledged and open per gate (acks read from `verification/*.json` and `overlay/*.json`); exit 0 on a frozen corpus, 1 on a batch with an open finding or an unused ack. Baseline on the frozen `expansion.v1`: [label-evidence lint](card-pipeline-internals.md#label-evidence-lint-deterministic) |

Accept gates per stage:

- **research.** A strict schema (no numeric field; IDs `<issuer-slug>-<card>`; https URLs on the issuer's domain allow-list; enum kinds, groups, networks; notes at most 300 characters; provenance `card-researcher`, model, date, `agent-research-unverified`; no card of a released corpus of the build config unless the batch is a refresh), then `build-expansion-cards.mjs --dir` writes `cards.json`, `sources.json`, `exclusions.json`, `capture-hints.json` (the Phase 7 card and page lists, such as `ALREADY_LABELED`, `MERGED_VARIANTS`, `SKIP_URL` and `PICK`, apply to the default run only).
- **verify.** Findings parse (`verificationFileSchema`, with optional `packetId`, `batch`, `provenance`), provenance `agent-verified`, other cards' entries unchanged, every packet card present, `current` equals the draft (for an undrafted card, the empty reference, and `confirmed` is refused), `verifier.filesRead` names every capture of the packet's cards, quotes verbatim and at most 25 words (`applyVerification`). A card whose verify was accepted before it became undrafted gets a second verify packet and then a second adjudicate packet: the verifier appends to `verification/<issuer>.json`, the scope gate keeps accepted entries byte for byte and refuses a second entry for a card. The file's `verifier` block names the latest verifier; each card's verify run stays in `state.json`.
- **adjudicate.** `adjudicator` filled, every finding and drop-card decided, the verifier's findings and block unchanged, `apply --check` on the batch passes; the label lint (checks a–c) runs on the corpus case apply will write for each packet card, through the same in-memory `applyVerification`, every label-lint ack must name a finding the lint raises there, and every finding the acks leave open is a gate error (`label lint: rate <cardId> rules.N.rateBps`), so the adjudicator's dry run shows what to fix or ack and apply stays a backstop. Label-lint acks of cards outside the packet must be unchanged; the verifier writes none. Refuses a run that verified any packet card and a packet claimed before verify was accepted.
- **overlay.** The fragment parses (overlay entry schemas plus program mappings), covers exactly the packet's cards, every `corpusCaseSha256` is `sha256Json` of the card's corpus case, the batch merged as the newest layer of the build config passes `mergeLayers` and `checkOverlay` for the issuer, no gate, program or program-detail ID that another issuer's fragment in `overlay/` defines is given other content, the label lint passes (acks counted apart); then the fragment is merged into `catalog-overlay.json` and `reward-programs.json`.
- **Every agent stage** runs the quote and adjacency check (`scripts/lib/expansion-quote-check.mjs`, the function behind `check-expansion-quotes.mjs`, which also scans `research/` and `overlay/`) on the batch's captures; research passes it where no capture exists yet.

## Eval and handoff

| Command | Behaviour |
| --- | --- |
| `eval [--batch B] [--cross-model-run DIR]` (also `run eval`) | Refuses until build is done. Runs `expansion-pipeline-metrics.mjs --dir <batch> --output <tmp>` (draft → verified correction rates, findings accepted/modified/rejected, rules added/removed, cards confirmed/fixed/dropped) and, when every corpus card's trace and capture is in the batch, `score-expansion-traces.mjs --dir <batch> --captures <batch>/captures --traces <batch>/extractions --output <tmp> [--run DIR]` (luna re-score, an upper bound; the cross-model run when given); otherwise the re-score is `inputs-missing` and eval still records the metrics. Without `--cross-model-run` it prints the gpt-5.5 `low` command through `score-expansion-traces.mjs --print-command --dir <batch>`; the coordinator starts that run, never the CLI. Scoring calls no model, so it is not refused under `CI`/`RENDER`. Writes the text-free, timestamp-free (apart from state's own stage times) `pipeline/eval.json` and records eval done with its SHA-256 |
| `handoff [--batch B]` | Prints markdown and writes nothing: the PR checklist (branch, the checks, the quote check with every capture folder, wiki lint, wiki pages, an independent reviewer subagent); the build report summary recomputed through the builder (version, verifiedAt, expiresAt, oldest source date, cards, rules, bytes against the budget, layers, held-out and dropped cards with reasons, the batch's own counts, rule IDs kept, changed old → new, added and dropped; a proposed build's config, saying nothing ships); migrations new against `origin/main`; review-app readiness; the capture folders (absolute paths, cited sources per folder, files present and matching here, and as `--captures` flags); the publish steps of [catalog release](../ops/catalog-release.md) with the release version and expiry; and the statements that nothing is published without Evan's approval of that release and that labels are agent-verified, not human-verified. Exits 1 with the reasons when the batch is not ready: research or a card stage not done (dropped and held-out cards excepted; a stage recorded done whose gitignored inputs are not on this machine is a warning), open packets, build or eval not done, `eval.json` missing or changed, the batch not a layer of `catalog-batches.json`, the catalog failing to build, or the catalog version already on `origin/main` with other contents. With no batch it describes the current catalog and exits 1 |

`eval.json` holds `pipeline` (the metrics script's output without its prose definitions), `traces` (`scored` with the scorer version, corpus hash and the all/drafted/undrafted/by-issuer counts and rates, or `inputs-missing` with a count), `crossModel` (`not-run`, `inputs-missing` or `scored`), `agreement` and `timings`. **Agreement** compares, for each batch card that is also in the frozen `expansion.v1`, the batch's verified labels with the frozen ones: rules paired within a category by the v2 scorer's `matchRules` (closest issuer wording, then an equal rate), per-field agreement on matched rules (`rateBps`, `paidOnPaymentBps`, `cap`, `activation`, `usMerchantsOnly`, `limitedTime`), card fields (`rewardCurrency`, `pointValueHundredthsOfCent`), rules on one side only (by category), exclusion and issue counts, per card and overall. `cardsIdentical` counts cards with the same rules, rule and card field values, and the same exclusion and issue counts (texts are not compared). It is labelled `agreement-not-accuracy`: both label sets are agent-verified. **Timings** come from state (per stage: records, done, attempts, pauses, first and last `finishedAt`/`acceptedAt`, models) and from the batch's `extraction-summary.json` (model minutes, input and output tokens per card and in total); `agentStages` sums the `durationMs` and `tokens` that `accept` recorded on the issuers' agent-stage records (model minutes, tokens, and both divided by the batch's cards), `null` when none was recorded; `startedAt` is not recorded, so it is `null`, never estimated. The acceptance run's measurement is [`docs/evals/pipeline-v1.md`](../../docs/evals/pipeline-v1.md).

**Review-app manifests.** The hosted review app knows capture hashes from the manifests [`apps/review/src/manifest.ts`](../../apps/review/src/manifest.ts) bundles at build time: the fixed `real/manifest.json`, `real/merchant-manifest.json`, `expansion/manifest.json`, every `evals/curation/batches/*/manifest.json` (eager `import.meta.glob`) and every `evals/curation/freshness/*.json` (Zod-guarded, a malformed record skipped; each `unchanged` entry is a capture of its hash dated the record's day). It keeps every capture recorded for a source ID and requires the one dated the catalog source's `checkedOn` when there is one, otherwise the newest-dated one, so a refreshed source accepts only its new capture. `handoff`'s `readReviewManifests` parses the same imports and expands the globs (it throws if either shape is gone), and `reviewAppReadiness` lists a cited source with no bundled hash (`missing`) or whose hash is not among the captures its `checkedOn` selects (`differs`). This blocks publishing, not the PR, so it does not change the exit status. The hosted app knows a batch only after it is merged and Render deploys `main`.

## Freshness

| Command | Behaviour |
| --- | --- |
| `freshness [--date YYYY-MM-DD] [--only sourceIds] [--concurrency N]` | No model; refused under `CI`/`RENDER`. Re-renders every source the build config's catalog cites (`citedSourceIds`: the first ten sources of each included card, issuer-stated program valuations, the merchant MCC pages), each with the manifest hash and layer the builder takes (`effectiveSources`; `merchants` for the MCC pages) and that layer's capture hint, through `capture-issuer-pages.mjs`, one process per host (2.5 s between its pages, up to N hosts at once, default 4) into a `pipeline-freshness-*` directory under `os.tmpdir()` that is deleted in all cases. Writes `evals/curation/freshness/<date>.json` (Zod, strict, text-free) after each host: per source `{ sourceId, layer, manifestSha256, sha256 \| null, result, flags, checkedOn }` with `unchanged` (the manifest's hash), `changed` (another hash, no problem flag), `flagged` (another hash with `http-error`, `short`, `bot-wall` or `fetch-failed`) or `unreachable` (nothing rendered; `fetch-failed`), the renderer (capture script SHA-256, Playwright, Chromium) and counts per result (the false-change measurement). A re-run on the same date resumes (sources missing from that day's record, unreachable there or re-hashed since); `--only` re-checks exactly those. A record holds one renderer: if the capture script's hash differs from the day's record, a plain run re-checks every source and `--only` is refused. A `--date` after today is refused; `pipeline-freshness-*` directories older than an hour are removed at start. Prints counts per layer and result, the cards with a changed source per issuer with their `init` command, and the flagged and unreachable sources |

**Builder dating** (`scripts/lib/catalog-batches.mjs`, `catalog-v3.mjs`, `freshness.mjs`): a manifest source's effective date is the newest `checkedOn` of a freshness record that found it `unchanged` with that manifest `sha256`, when newer than its own `checkedOn ?? capturedOn`; the merchant MCC sources' `checkedOn` in `merchants.json` is overridden the same way from `real/merchant-manifest.json`'s hashes. Only `unchanged` dates a capture: a `changed` hash could equal an older layer's capture of the same source and out-date the newer batch's. `verifiedAt` is the newest effective date of the cited issuer sources; before the overlay check the builder checks every cited source against the 30 days before `verifiedAt` and fails with the stale source IDs and dates. With no record the build is unchanged.

**Real cards in batches.** A pipeline batch (never a base layer) may replace one of the seven real cards; `mergeLayers` lists it in `replacedReal`, the catalog keeps `REAL_CARDS` names and the release-1 rule-ID scheme (`<prefix>-<category>`, `-2` for a repeated category), `checkRealCards(…, { replaced })` skips it (the others stay pinned to release 1), the ledger continuity check applies and the build report and `handoff` name it with every category whose excluded payment paths differ from release 1 (`realPaymentPathChanges`), so a dropped exclusion is visible. Its overlay entry comes from the batch, so the Amex BNPL exclusion that `applyOverlayCard` adds only to a card without an entry must be in the batch overlay (`.claude/agents/card-overlay-author.md`).

| `publish … --confirm <v> --instruction-at <ISO UTC>` | `--confirm` must equal `--version`; the instruction time not in the future (5 min skew) nor older than 7 days; git checks refuse. Resumes the newest pending draft of the version or creates one on the head; refuses a draft whose catalog's canonical JSON SHA-256 is not `CATALOG_V3`'s or whose base is not the head (no automatic rebase); uploads only sources not attached with the local hash and date (429: `Retry-After` bounded 1–60 s, default 15 s, at most 8 waits per source; progress every 25); checks each returned `content_hash`; `PUT` with exactly one matching capture per source (skipped when already so); re-reads and verifies; publishes with `expectedRevision`, `expectedHash`, `expectedHead` and the note (agent-verified, not human-verified; what was checked; Evan's instruction time); checks `/v1/catalog` serves it |

Every request: timeout, `redirect: 'error'`, `cache: 'no-store'`, bounded bodies; errors print the HTTP status and the API's `error` code only, never a body, token or password; a 401 refreshes the session once and retries once; the rotated refresh token is saved before the access token is used; a session file group or others can access, a symlinked session file or directory, or one another user owns is refused; `publish --confirm` checks the session's API before refreshing it.

## Known gaps

- Nothing records a `scope-question` or `convention-needed` reason in `state.json`, so those queue items never appear: the skill asks scope questions before `init` and handles `convention-needed` reported by an agent by releasing the packet.
- `batch.json` is strict and has no field for Evan's answers, so the skill puts them in `--summary` at `init`.
- A session must start after the skill and agent files it uses are merged (it loads them at start-up).
- `run capture` runs sequentially (2.5 s between pages) rather than in parallel per host; the apply and capture scripts print their own output (which may quote captures) to the terminal.
